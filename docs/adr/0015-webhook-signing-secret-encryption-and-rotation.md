# ADR-0015: Webhook signing-secret encryption and rotation

- **Status:** Accepted
- **Date:** 2026-08-01
- **Decision owners:** SettleFlow Project
- **Reviewers:** Project owner through Webhook Endpoint Foundation approval
- **Supersedes:** None
- **Superseded by:** None

## Context

SettleFlow must later sign outbound webhook payloads, so unlike merchant API keys it must be able to recover webhook signing secrets. Persisting plaintext or only a one-way hash cannot meet that need safely. Endpoint creation and rotation also need one-time secret display, explicit versioning, a bounded overlap window, and auditable state changes.

The specification authorizes encrypted webhook secrets, current and previous secret support during rotation, one-time display, and production key management. The repository needs a precise cryptographic-storage and rotation boundary before endpoint tables or APIs are designed.

## Decision drivers

- Recover a signing secret only inside the future delivery boundary.
- Never persist or log plaintext signing material.
- Detect ciphertext tampering and key/configuration mismatch.
- Support safe local development and a future managed production KMS.
- Limit rotation overlap while allowing merchants to transition verifiers.
- Keep endpoint mutation, secret version, and audit evidence atomic.

## Considered options

### Option A: Versioned AES-256-GCM envelope with keyring abstraction and bounded overlap

Generate a high-entropy secret, encrypt it with authenticated encryption and contextual associated data, identify the encryption key, and store versioned current/previous secret records. Use a local keyring adapter now and preserve a provider boundary for a future production KMS adapter.

### Option B: Persist only a secret hash

A hash supports verification of inbound credentials but cannot sign an outbound payload. It is rejected.

### Option C: Persist plaintext or application-obfuscated secrets

Database disclosure would immediately expose every endpoint secret. It is rejected.

### Option D: Require a production KMS provider for local development

This would couple the local case-study foundation to an external production service. It is rejected, but production readiness remains gated on the future KMS adapter.

## Decision

The decision is **Option A**.

### Secret and encryption contract

- A webhook signing secret is `whsec_` followed by the unpadded base64url encoding of **32 cryptographically random bytes**. It is generated by the server and shown only in the successful creation or rotation response.
- Persist no plaintext secret, plaintext copy, recoverable log field, API response snapshot, or telemetry attribute.
- Encrypt with **AES-256-GCM** using a unique cryptographically random 96-bit nonce and a 128-bit authentication tag for every encryption operation.
- Bind ciphertext to immutable context with authenticated additional data containing a versioned encoding of merchant ID, endpoint ID, secret version, encryption algorithm, and key ID. Decryption fails closed when any bound value or authentication tag differs.
- Persist the ciphertext, nonce, authentication tag, encryption key ID, secret version, lifecycle state, creation time, and overlap expiry where applicable. These values remain Webhooks-owned signing metadata.

### Key-management boundary

- Application code depends on a narrow keyring/KMS port that can identify the active encryption key and decrypt by key ID. Domain and API code never read raw master-key configuration.
- The first implementation uses a local keyring adapter. Its key material comes only from ignored local secret configuration, never the database, repository, safe example files, logs, or API.
- The adapter supports one active encryption key and a bounded decryption keyring so key replacement can be forward-only. New writes use the active key; old key IDs remain decryptable until an authorized re-encryption process finishes.
- A production KMS/envelope-encryption adapter is required before any production-readiness claim. The provider/vendor and operational key-rotation process remain a future, separately reviewed implementation decision.
- Missing, malformed, unavailable, or unknown key material fails closed. Readiness and operational behavior for the selected production adapter must be defined with that adapter.

### Endpoint-secret rotation

- Each endpoint has exactly one current secret and at most one previous secret eligible for overlap. Older secret material is retired and unavailable to future signing.
- Rotation requires the endpoint precondition contract in [ADR-0016](0016-webhook-endpoint-api-ownership-and-subscriptions.md). The server generates and encrypts the new secret before the database transaction, then the transaction promotes the current secret to previous with an expiry exactly **24 hours** after the rotation time, retires any older previous version, inserts the new current version, increments the endpoint version, and appends the required Operations audit event.
- If any persistence or audit operation fails, the endpoint version and stored secret lifecycle do not change. The uncommitted plaintext is discarded.
- The new plaintext is returned only after the transaction commits and only in that rotation response. If the client loses it, SettleFlow does not recover or redisplay it; the client performs another preconditioned rotation.
- Future webhook delivery supports the current secret and, until its expiry, the previous secret. The exact versioned signature-header representation is decided before HTTP delivery is implemented; it must not extend the 24-hour overlap or expose either secret.
- Expiry is enforced by time when selecting signing material. A future cleanup job may remove retired ciphertext in bounded batches only after an approved retention plan; delivery must not depend on cleanup having run.

Project-owner approval accepts the secret format, AES-256-GCM storage, local keyring/future KMS boundary, current/previous lifecycle, and 24-hour overlap above.

## Consequences

### Positive

- Database disclosure alone does not expose usable signing secrets.
- Authenticated encryption detects tampering and context substitution.
- Merchants can transition verification during a fixed overlap.
- Local development remains self-contained behind the same abstraction needed by a future KMS.

### Negative

- Webhook delivery depends on decryption-key availability.
- Rotation and key replacement require explicit version/lifecycle records.
- One-time display means a lost response requires another rotation.
- A production KMS adapter and operations procedure remain required.

### Risks and mitigations

- **Nonce reuse:** Generate a fresh 96-bit nonce for every operation and test deterministic injected-collision/failure paths without permitting reuse.
- **Ciphertext swapping:** Bind merchant, endpoint, version, algorithm, and key ID as authenticated additional data.
- **Key leakage:** Load keys only through the adapter, redact configuration/errors, and scan logs and committed files.
- **Unbounded overlap:** Enforce the 24-hour expiry in selection logic and allow no more than one previous secret.
- **Lost one-time response:** Document immediate re-rotation; never create a durable plaintext response snapshot.
- **Local adapter used as production KMS:** Fail production readiness/deployment policy until an approved production adapter is configured.

## Implementation notes

- Cryptographic operations and random generation occur outside the database transaction; only encrypted records and metadata enter persistence.
- Plaintext should have the narrowest practical in-memory lifetime and must not appear in thrown error context.
- Rotation is not a generic endpoint update and has its own command/route.
- Exact schema names, cryptographic adapter dependency choices, production KMS provider, and signature-header encoding belong to their approved implementation plans.
- This ADR milestone creates no secret, endpoint, API, schema, keyring, or delivery implementation.

## Affected requirements and invariants

- **Requirements:** FR-09 endpoint/secret lifecycle; FR-10 signed webhook delivery; FR-13 safe errors; FR-14 lifecycle audit.
- **Invariants:** No financial invariant changes. Tenant ownership, append-only audit, and secret-redaction controls apply.
- **Acceptance:** Known-vector, tamper, AAD-swap, key-ID, rotation-overlap, one-time-display, rollback, concurrency, and leakage tests are required when implemented.

## Impact assessment

- **Affected modules and dependency direction:** Webhooks owns secret metadata and uses an infrastructure keyring port; Operations receives audit commands through a stable port.
- **Financial invariants and money representation:** None.
- **Database schema, migration, locking, and transaction boundaries:** Future versioned secret records and endpoint version locking are required; rotation and audit commit atomically.
- **Idempotency, outbox/inbox, retries, and partial failure:** A failed rotation is retryable with a fresh precondition; no plaintext idempotency snapshot is permitted.
- **API, event, webhook, or CSV compatibility:** Establishes the public secret format and 24-hour compatibility overlap.
- **Authentication, authorization, secrets, SSRF, and sensitive data:** Directly defines encryption, key ownership, display, and redaction boundaries.
- **Observability, alerting, and runbooks:** Record only key ID/version and stable failure classes; alert on keyring/KMS failures without secret data.
- **Production dependencies and supply-chain impact:** Local implementation may use Node.js cryptography; future KMS adapter requires separate review.

## Verification

- Verify secret format, entropy source, one-time display, absence from subsequent reads, and log/error/snapshot redaction.
- Verify AES-GCM round trips and rejection for changed ciphertext, nonce, tag, AAD fields, or unknown key ID.
- Test concurrent rotations with the same/stale ETag, exact version increments, one current/at-most-one previous row, and atomic audit rollback.
- Test time boundaries immediately before and at the 24-hour expiry with an injected clock.
- Prove repository/example configuration contains no usable encryption key and production policy rejects the local adapter.
- Add future delivery signature vectors for both supported secret versions before enabling outbound HTTP.

## Rollout and recovery

Introduce the keyring abstraction and encrypted schema before endpoint creation. Back up key metadata separately from ciphertext and verify recovery in a non-production environment. Never roll back by writing plaintext. A key/configuration incident disables signing and follows a controlled key replacement/re-encryption plan with preserved audit evidence.
